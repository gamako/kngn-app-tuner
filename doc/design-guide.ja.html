tuner / design guide

音を受け取り、
中心を光らせる。

Tunerは、Native・CLI・WebAssemblyで同じピッチ解析器を共有するクロマチック・ギターチューナーです。このページでは、音声が入力されてから画面の針になるまでを説明します。

全体像 データ経路 入力抽象化 ピッチ解析 GUIメーター WebAssembly 検証

まず覚える3つの層

INPUT

音声を取り込む

マイク、WAV、テスト用サイン波を、モノラルの f32 サンプル列にそろえます。

CORE

音程を判定する

pitch.Analyzer が自己相関から周波数、音名、cents、信頼度を求めます。

VIEW

結果を見せる

GUIは同じ判定結果を、音名・Hz・半円スケール・針・状態色として表示します。

設計の中心：入力方式を増やしても、ピッチ解析器とGUIを複製しない。入力だけを差し替え、中央のPCM経路へ合流させます。

データ経路

3種類の入力は入口こそ異なりますが、リングバッファの後ろは共通です。

入力アダプターはイベント/RT境界を担当し、解析と描画はアプリケーションスレッドで行います。

入力抽象化

NATIVE

src/input_native.zig

kngnの kit.audio.requestCapturePermission() と openCapture() を使います。音声コールバックは固定リングバッファへサンプルを追加するだけです。

マイク許可の状態は requesting、ready、denied などに変換してGUIへ渡します。

WASM

src/input_web.zig

ブラウザ側から固定バッファへPCMを受け取り、Nativeと同じリングバッファへ流します。ブラウザAPIの非同期処理は web/tuner.html が担当します。

Wasmの公開境界は tuner_capture_* 関数に限定しています。

callback / Worklet音声を受け取る
→
固定バッファ境界を短くする
→
リングバッファ解析側へ受け渡す
RTの約束：音声コールバックにアロケーション、ロック、ファイルI/O、GUI操作を入れません。サンプルをリングへ入れたら、解析は別のアプリケーションスレッドで行います。

ピッチ解析

src/pitch.zig の Analyzer は、録音を「音名」と「基準音からのずれ」に変換します。ここでは、低いE弦を例に処理を追います。

1 / 8192 samples

波形をためる

入力はモノラルの f32 サンプルです。8192サンプルの窓を作り、2048サンプルずつ重ねながら更新します。

2 / lag

周期を探す

波形を少しずつずらして、元の波形とどれだけ似ているかを調べます。最も似るずらし量が周期です。

3 / cents

音名とずれへ

周期からHzを求め、12平均律で最も近い音名を選び、基準周波数との差をcentsにします。

自己相関は「同じ形がもう一度現れる場所」を探す

Analyzerは、入力を lag サンプルずらして積を足します。周期と同じlagでは、山と山・谷と谷が重なるためスコアが大きくなります。コードでは60〜500Hzに対応するlagだけを探索します。

なぜピークの位置を補正するのか

実際の周期が整数サンプルにならないことがあります。そこで、ピークの左右3点 y0, y1, y2 を使って放物線の頂点を近似し、best_lag に小数の補正を加えます。

refined_lag = best_lag + correction
frequency = sample_rate / refined_lag

信頼できない結果は表示しない

まずRMSで音量を確認し、rms < 0.008 なら no_signal。相関の信頼度が 0.18 未満、または周波数が60〜500Hzの範囲外なら unstable にします。

このため、無音や雑音を無理に音名として表示しません。

周波数から音名とcentsを求める

まず12平均律の最近傍MIDIノートを選び、そのノートの基準周波数と比較します。1半音は100 centsです。

midi_float = 69 + 12 × log2(frequency / 440)
target = 440 × 2^((midi - 69) / 12)
cents = 1200 × log2(frequency / target)

GUIメーターの設計

FLAT0SHARP
VIEW

実用性を先に、演出は短く

針は0.22係数で追従させ、入力の揺れをそのまま画面へ出さないようにしています。

中央の正確ゾーンは緑、近傍はアンバー、遠い位置は暗い目盛りです。正確になった瞬間だけ中心の発光が目立ちます。

描画は Context.custom と DrawList の少数の線・矩形で構成し、全画素ループやRT経路の処理は追加していません。

WebAssembly版の境界

ブラウザのマイク許可は非同期で、NativeのようにWasm内部から直接取得できません。そのため、ブラウザ側とWasm側を小さなABIで接続しています。

1

許可を取る

getUserMedia でモノラル・エコー抑制なしの入力を要求します。

2

Workletで集める

AudioWorklet と SharedArrayBuffer のリングで音声処理とメインスレッドを分離します。

3

Wasmへsubmit

固定バッファへコピーして tuner_capture_submit を呼び、共通リングへ合流させます。

tuner_capture_buffer_ptr()
tuner_capture_buffer_len()
tuner_capture_get_state()
tuner_capture_set_state(code)
tuner_capture_submit(frames, channels, sample_rate)
ブラウザでの注意：file:// ではマイク入力を動かせません。zig build package-web 後、COOP/COEPヘッダーを付けたサーバーで配信してください。

検証方法

自動テストとビルド

zig build test
zig build gate-web
zig build package-web

ピッチ判定、リングバッファ、入力状態、Wasmパッケージを検証します。

決定的なGUI確認

KNGN_HEADLESS=1 \
KNGN_HARNESS_SCRIPT=tests/gui-events.txt \
KNGN_HARNESS_OUT=/tmp/tuner-harness \
zig build run-tuner -- --input tone --frequency 82.4069

テスト音ならマイク許可に依存せず、メーターの中央一致やずれた針を確認できます。

実機マイクを確認するとき
zig build run-tuner を実行します。GUIはデフォルトでマイク入力です。macOSではシステム設定の「プライバシーとセキュリティ → マイク」で許可し、ギターの音を入力します。
問題をWAVで再現するとき
CLIの --input file path/to/input.wav を使います。マイク依存のタイミングや権限を切り離し、同じ pitch.Analyzer を再現可能な入力で確認できます。
